# ADR-006: Narrow the Knowledge Graph to Traceability and Validation

**Status:** Accepted

---

# Context

`adr/ADR-001-knowledge-graph.md` decided that PyFlow would model project
knowledge as a typed property graph, and that the graph would be the
authoritative planning model. It went further: "planning artefacts such
as capability trees, dependency graphs, roadmaps and release plans will
be generated from this model wherever practical," and "the graph itself
is considered the source of truth. Generated views are not."

That decision was made on 2026-08-12, before any of the documents it
describes existed. Eleven `planning/**.yaml` files were created empty and
stayed empty. On 2026-08-21 a repository audit found the ADR reading as a
description of a repository that does not exist -- accepted, unqualified,
and pointed at by the root `CLAUDE.md` as the record of the project's
architecture. ADR-001 now carries an Implementation Status section
recording that gap; this ADR is the decision that closes it.

Three things are now known that were not knowable in August:

**The roadmap cannot be a generated view.** `docs/planning/roadmap.md` is
1,457 lines, and the overwhelming majority is *reasoning*: why a
decision was made, what amendment followed which bug, what an exit audit
found. That prose is the institutional memory this entire repository is
organised around (P-001, P-013, P-014). Generating it from a graph would
either discard the reasoning or reduce the graph to a store of prose
blobs keyed by id -- a database, not a model. The same applies to
`docs/planning/releases.md`, which is an argument for *not* having a
release process rather than a list of releases.

**Some of the content genuinely is graph-shaped, and prose is holding it
badly.** `docs/handbook/numerical-methods/compatibility.md` is 313 lines
of explicitly typed pairwise relationships -- seven named relationship
kinds across eight method families -- which is a typed property graph
written out longhand. And the cost ADR-001 predicted is already being
paid: `docs/planning/dependency-tree.md` and
`docs/architecture/engine.md` describe *different* subsystem trees
today. Both documents say so, in two separate open backlog items, and
the divergence has survived every consistency review since 2026-08-17
because nothing checks it. Capability Level 7 is a second instance: it
has no corresponding roadmap Stage, so the "Dam Break" golden demo is
unreachable from the roadmap -- a dangling edge that has needed a human
to remember for weeks.

**There is a standing constraint pulling the other way.** The root
`CLAUDE.md`'s Planning Philosophy: "The planning system exists to
accelerate PyFlow. Avoid spending time improving the planning system
unless it directly benefits development of PyFlow." ADR-001 as written,
plus P-002 ("everything that can reasonably be generated should be
generated"), point one way; that rule points the other. Both are in
force, and leaving the tension implicit is what let the graph sit
unbuilt and unexplained for ten days.

---

# Decision

ADR-001 stands. The graph remains the authoritative model **for the
relationships between project entities**. Its scope is narrowed as
follows.

**1. The graph holds entities and the relationships between them.** Not
reasoning. An entity carries an id, a name, a short description, and
typed edges to other entities. Why a component exists, what a bug
taught, and what an amendment corrected stay in prose.

**2. Prose is authoritative for reasoning, and is never generated.**
`roadmap.md`, `backlog.md`, `CHANGELOG-DESIGN.md`, the Handbook and the
ADRs are written, not rendered. This reverses ADR-001's "roadmaps and
release plans will be generated" specifically, and nothing else.

**3. A document becomes a generated view only when generating it is
cheaper than maintaining the duplicate, *and* the result is checkable in
CI.** `docs/index.md` is the working precedent: generated by
`tools/generators/`, verified by `make check-docs-index`, and it earns
its keep. A generated view that nothing checks is a second source of
truth with extra steps.

**4. The graph's primary product is validation, not generation.**
`make check-graph` fails on a dangling edge, an undeclared relationship
type, a reference to a file that does not exist, or a dependency cycle.
This is where the value actually is: the two live inconsistencies above
are both things a validator catches for free and a human reviewer has
demonstrably missed for weeks.

**5. A known, accepted gap must be declared, not merely absent.** An
entity that ought to have an edge and does not carries an `unresolved:`
field stating why. Capability Level 7 is the worked example. An
undeclared missing edge is an error; a declared one is a visible open
question, which is what the backlog has been doing by hand.

**6. Entity categories are populated when their content exists and
something consumes it**, not up front. `planning/data/` keeps its seven
files, and `planning/data/CLAUDE.md` records, per file, whether it is
populated and what would trigger populating it. `releases.yaml` in
particular stays empty for as long as `docs/planning/releases.md` argues
that PyFlow should not have a release process -- an empty file matching
a documented deliberate absence is correct, not incomplete.

---

# Consequences

## Positive

- ADR-001 stops describing a repository that does not exist.
- The `dependency-tree.md` / `engine.md` divergence is resolved by
  construction rather than by choosing which document to edit: the tree
  becomes a generated view of the component graph, whose shape follows
  `engine.md`'s nine conceptual layers. This also closes the open
  backlog item asking whether that document should be derived.
- Dangling relationships fail CI instead of waiting for someone to
  notice. Level 7 becomes a declared open question rather than an
  informal memory.
- The Planning Philosophy is satisfied rather than overridden: the work
  is bounded by rule 3, and each generated view has to justify itself.

## Negative

- Two sources of truth remain in a real sense -- entities in YAML,
  reasoning in Markdown -- and they can drift. Rule 4's validator checks
  that referenced files *exist*, not that the prose in them agrees with
  the graph. That is a genuine limitation and is not being papered over:
  the same limitation `make ci` already has for documentation content
  generally (root `CLAUDE.md`, "For documentation it verifies structure,
  not content").
- Anyone adding an engine component now has two places to touch. The
  Blast Radius rule already covers this, and `make check-graph` makes
  forgetting one of them a CI failure rather than silent drift, which is
  the trade being accepted.
- Deciding per-document whether generation is worth it (rule 3) is a
  judgement call each time, not a rule that decides itself.

# Alternatives Considered

## Schedule the full graph as ADR-001 describes it

Rejected. It requires an answer for the 1,457 lines of roadmap reasoning
that cannot be generated, and none of the available answers are good.
It would also create `releases.yaml` with nothing to hold, which is the
same mistake E9 and E10 retired directories for
(`docs/planning/backlog.md`): structure built ahead of any content or
consumer.

## Supersede ADR-001 and accept hand-maintained planning documents

Rejected, though it was close, and P-016 (prefer reversible decisions)
argues for it. What defeated it is that the two live inconsistencies are
not hypothetical costs -- they exist, in the repository, today, and both
are exactly the class of error a typed graph eliminates mechanically.
Retiring the graph would mean fixing them by hand and accepting the next
one.

## Keep ADR-001 as written and simply note it is unimplemented

Rejected. That is the state the 2026-08-21 audit found, and it is how a
decision stays unmade indefinitely: the note explains the gap without
anyone ever having to close it.

# Notes

This ADR narrows ADR-001's scope; it does not replace it. ADR-001 stays
Accepted, and the pair should be read together -- the same relationship
`ADR-004` (compute-and-rendering class) and `ADR-005` (instances)
already have, where the later ADR settles a space the earlier one
deliberately left open.
